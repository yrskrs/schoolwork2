# Оновлення SchoolNet v4.1.23: Ізоляція лічильників моделей та автоматичний збір/аналіз помилок ШІ

## 1. Проблема та мета оновлення

1. **Дублювання лічильників запитів**:
   Коли вчитель додавав декілька підключень з однаковою назвою моделі (наприклад, декілька облікових записів Google Gemini з моделлю `gemini-2.5-flash`), підрахунок успішних та помилкових перевірок у таблиці черги виконувався за рядком назви моделі `ai_model_used`, через що обидва акаунти показували однакові цифри.
2. **Аналіз збоїв API та передача на виправлення**:
   Раніше журнал помилок ШІ лише накопичував технічні записи. Було потрібно створити зручний інструмент, який:
   - Автоматично зчитує всі накопичені помилки в один клік.
   - Позначає їх як прочитані (щоб було зрозуміло, які помилки нові, а які вже пройшли аналіз).
   - Передає дані моделі для аналізу та створення структурованого технічного звіту.
   - Надає однозначний вердикт: чи це зовнішня проблема провайдера (429 Rate Limit, 503 Overload, вичерпана квота, тайм-аут мережі), де код правити не потрібно, чи це проблема коду/формату (400, помилка JSON-парсингу), що вимагає втручання розробника.
   - Дозволяє в 1 клік скопіювати звіт для передачі сторонньому ШІ-асистенту.

## 2. Реалізовані зміни

### 2.1. База даних та моделі (`feed/models.py`, міграція `0055`)
- Додано `ai_connection_id` у `Submission`.
- Додано `connection_id`, `is_read`, `read_at` у `AIErrorLog`.
- Додано `connection_id` у `AIRequestLog`.
- Створено нову модель `AIErrorReport`:
  - `created_at`: дата та час формування звіту.
  - `created_by`: вчитель, що ініціював аналіз.
  - `errors_count`: загальна кількість проаналізованих помилок.
  - `unread_count_before`: кількість нових незчитаних помилок на момент аналізу.
  - `verdict`: системний статус (`external_issue` | `needs_fix` | `no_errors`).
  - `verdict_title`: текстовий висновок українською мовою.
  - `report_text`: повний Markdown-звіт для розробника або ШІ.
  - `model_used`: назва моделі, що аналізувала помилки.

### 2.2. Сервіс обробки та обліку (`feed/gemini_service.py`)
- Функція виклику API `call_ai_api` та логування `log_ai_request_metric`, `log_ai_error` тепер обов'язково приймають та зберігають `connection_id`.
- Під час збереження перевіреної роботи встановлюється `submission.ai_connection_id = current_connection_id`.

### 2.3. Ізольований розрахунок `model_stats` (`feed/views.py`)
- У таблиці черги моделей кожен рядок фільтрує роботи за `ai_connection_id=conn_id`.
- Помилки черги враховуються з `AIErrorLog.objects.filter(connection_id=conn_id)`.
- Для кожного підключеного акаунта відображається точна персональна статистика перевірок.

### 2.4. Модуль діагностики ШІ (`feed/ai_error_analyzer.py`)
- `get_error_summary_stats()`: формує статистику за HTTP-кодами, провайдерами, статусами читання.
- `classify_errors_heuristically()`: надійний евристичний класифікатор (відокремлює зовнішні 429/503/таймаути від 400/JSON-помилок).
- `generate_error_report_with_ai()`:
  - Позначає незчитані помилки як прочитані.
  - Формує агреговані технічні пакети.
  - Викликає модель зі спеціальним системним промптом діагностики веб-платформи.
  - Має вбудований безвідмовний fallback на евристичний генератор звіту (на випадок повної відсутності інтернету чи блокування ключів).
  - Зберігає звіт у таблицю `AIErrorReport`.

### 2.5. Інтерфейс користувача (`templates/feed/components/ai_error_analysis.html`)
- Підвкладки «📋 Список помилок» та «🔬 Збір і аналіз помилок».
- Бейдж кількості незчитаних помилок.
- Кнопка запуску «🚀 Зчитати помилки та згенерувати звіт ШІ».
- Кольорові вердикт-банери (зелений при зовнішніх збоях, червоний при помилках коду, синій при відсутності помилок).
- Кнопка швидкого копіювання Markdown-звіту «📋 Скопіювати звіт для іншого ШІ».
- Історія згенерованих аудитів.
