# Аналіз звітів ШІ №2 та №3 — 14.10.2026

Джерело: збережені `AIErrorReport` №2 (21:19, 50 записів) і №3 (21:20, 11 записів) з локального сервера SchoolNet. Це агрегована діагностика без API-ключів, імен учнів та текстів їхніх робіт. Це 61 запис журналу, а не 61 окрема робота: одна перевірка може створити кілька записів.

| Причина | Записів | Висновок |
| --- | ---: | --- |
| `value too long for type character varying(40)` | 28 | Помилка збереження результату в PostgreSQL після отримання відповіді моделі. Поля `ai_score_level` / `student_ai_level` обмежувалися 40 символами. |
| Таймаути API | 11 | 7 у Gemini та 4 в OpenRouter. Повторна повна перевірка доступності перед кожною роботою додасть запит та очікування. |
| HTTP 502 / 503 / 504 / 429 | 17 | 7 / 6 / 2 / 2 відповідно: збої постачальників, перевантаження та квоти. |
| Непридатний формат / JSON | 3 | OpenRouter повертав `User Safety: safe` замість оцінювання. Таку відповідь не можна перетворювати на оцінку. |
| HTTP 400: mandatory reasoning | 1 | Для випадково обраного OpenRouter бекенду примусове вимкнення міркувань неприпустиме. |
| HTTP 413 | 1 | Запит після стиснення: 23,99 МБ при локальній межі OpenRouter 7,50 МБ. Потрібен інший маршрут або поділ завдання; не можна приховано вилучати докази з роботи. |

## Виправлення

- Історія містить посилання на кожен звіт. `report_id` визначає відображуваний і копійований текст; невідомий ID повертає 404. Лічильник останнього аналізу залишається прив'язаним до останнього звіту.
- Додано завантаження вибраного звіту як Markdown та сторінки історії по 10 записів. Старі звіти доступні незалежно від періоду статистики.
- Міграція `0060_submission_ai_level_text` змінює обидва поля рівня на `TextField`, зберігаючи повний текст та існуючі значення. Це усуває причину повторного звернення до моделей після вже отриманої відповіді.
- Для `openrouter/free` та `openrouter/auto` швидкий режим не надсилає `reasoning.enabled=false`. Для явно вибраної моделі, яка відхилила цей параметр з HTTP 400 та повідомленням про обов'язкові міркування, дозволено один запит із типовими налаштуваннями бекенду. Таймаути й сторонні помилки 400 цей повтор не запускають.

## Пропозиція для прискорення наступних перевірок

У поточній черзі використовуються хмарні Gemini, OpenRouter, Groq та Cloudflare. Запит «чи модель завантажена» корисний для власного Ollama: [`GET /api/ps`](https://docs.ollama.com/api/ps) повертає моделі в пам'яті. У хмарі [`models.list` Gemini](https://ai.google.dev/api/models) повертає каталог і можливості, без гарантії своєчасної відповіді наступної генерації. Перевірку каталогу варто кешувати, а не виконувати перед кожною роботою.

Рекомендований наступний крок: використати результати реальних запитів як короткочасний статус. Після таймауту / HTTP 502–504 пропускати проблемну модель на 60–120 секунд; для 429 враховувати строк відновлення квоти. Стан квот та авторизації потрібно розділяти за підключенням, а серверне перевантаження — за моделлю. Зараз cooldown прив'язаний лише до постачальника та моделі, а таймаут не завжди запускає паузу. Коли всі моделі на паузі, потрібен зрозумілий відкладений повтор, без багатьох послідовних дорогих спроб.

Чергу можна переглянути за виміряними затримками. У двох останніх успішних запитах `gemini-3.5-flash-lite` відповіла за 12,7–14,3 секунди. В одному ланцюжку перед нею витрачено 50,8 секунди на таймаут першого Gemini, 0,3 секунди на помилку OpenRouter та 37,1 секунди на HTTP 503 другого Gemini — разом приблизно 88 секунд. Це підстава перевірити її як перший маршрут; два запити ще не доводять довгострокову перевагу. Пріоритети користувача цим виправленням не змінюються.

[`openrouter/free`](https://openrouter.ai/docs/guides/routing/routers/free-router) випадково обирає модель серед придатних безкоштовних варіантів. Для стабільного формату оцінювання доцільно перевірити конкретну модель як основну, залишивши випадковий маршрутизатор резервом. [`Обов'язкові міркування`](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens) залежать від вибраного бекенду; приховування міркувань не звільняє вихідний бюджет токенів.

Ці зміни статусів і пріоритетів є пропозицією, а не частиною поточного патча.

## Перевірка

88 тестів пройшли на ізольованій SQLite та ще раз на окремій PostgreSQL-базі з образом виправлення. Перевірені відкриття звіту старішого за 10 записів, копійований текст, Markdown, екранування HTML, доступ лише після входу, некоректні ID, збереження довгого рівня без другого виклику моделі та сумісність параметрів OpenRouter. Реальні роботи учнів у тестах не оцінювалися.

`manage.py check`, `makemigrations --check --dry-run` та `git diff --check` пройшли.

Під час підготовки 4.4.15 додатково пройшли 16 тестів онлайн-оновлення. Окремо перевірено відповідність `VERSION`, JSON і Markdown-описів випуску, журналу сайту та версій Docker / Compose, а також відбір 4.4.15 як наступного випуску після 4.4.14.

## Розгортання та випуск

Виправлення спочатку застосовано до локального сервера як окремий образ на базі 4.4.14. Вебсервіс і ШІ-воркер пройшли healthcheck; перед активацією створено перевірену копію бази та медіафайлів. Серверна перевірка через `RequestFactory` з існуючим профілем автора підтвердила відображення й завантаження звітів №2 / №3, точний текст копіювання та відповідність SHA-256 початковим звітам. Зовнішній `/healthz/` повернув `ok`, а запит до звіту без авторизації — перенаправлення на вхід. Візуальна браузерна перевірка не виконувалася.

Для поширення підготовлено випуск **4.4.15** із записами у `VERSION`, `RELEASES.json`, `CHANGELOG.md`, журналі сайту та README; версії за замовчуванням Docker і Compose узгоджено. До журналу сайту також додано пропущений опис попереднього випуску 4.4.14.

Оновлення встановлює міграцію `feed.0060`; PostgreSQL підтверджує тип `text` без обмеження довжини для обох полів. Для відкату образу збережіть перевірену резервну копію та попередній образ за звичайною процедурою проєкту. Зворотне звуження полів до 40 символів потребує перевірки збережених даних.
