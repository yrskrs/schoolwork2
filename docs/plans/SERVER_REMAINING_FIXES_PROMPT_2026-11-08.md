Контекст:

- Сервер: `192.168.1.13`, SSH `yrsadmin`, каталог `/home/yrsadmin/schoolwork2`.

- Контейнери `schoolnet_app`, `schoolnet_ai_worker`, `schoolnet_postgres` здорові. Тимчасовий простій під час попереднього паралельного розгортання вже завершився.

1. **Приватні копії конфігурації та Git-стан.** Шість `.env.bak-*` мають права 0600, але не ігноруються Git. Спочатку захисти їх від випадкового коміту, зберігши резервні копії. `.dockerignore` вже виключає `.env*`, у перевіреному образі є лише `.env.example`; не стверджуй, що витік уже стався. Потім узгодь установлені файли з коректною Git-історією: серверний status містить 86 записів, а `scripts/update.sh` і `scripts/updater_service.py` відмовляються встановлювати оновлення з непорожнім status. Не використовуй сліпий reset або масове додавання файлів; не загуби встановлені виправлення. Самої чистоти status недостатньо: перевір узгодженість HEAD з дозволеним upstream і можливість штатного fast-forward. Не публікуй секрети чи непогоджені зміни в зовнішній репозиторій.

2. **Каталог Llama 4 Scout.** Увімкнена `@cf/meta/llama-4-scout-17b-16e-instruct`, але каталог повертає `supports_vision=false`, `max_images=0`. Cloudflare документує Vision. Виправ модельні метадані та відбір, не покладаючись на слова в назві. Підтвердь актуальні обмеження провайдера; перевіряй кількість зображень після адаптації PDF/Office. Не обрізай потрібні сторінки заради ліміту. Qwen Cloudflare вже визначається як vision/max_images=32, GLM як text/max_images=0 — не зламай це.

3. **Безпека HTTPS без поломки LAN.** Зараз `SESSION_COOKIE_SECURE=false`, `CSRF_COOKIE_SECURE=false`, HSTS=0; через HTTPS login реально повертає CSRF-cookie без Secure. Реалізуй належні Secure-cookie/HSTS для HTTPS/Funnel зі збереженням робочого LAN HTTP. Не вмикай глобальний HTTPS-редирект або Secure для всех HTTP-сценаріїв. Не довіряй довільним proxy-заголовкам без перевірки джерела. Використай наявний план `docs/plans/SECURITY_HARDENING_HTTPS_2026-11-08.md`. Перевір вхід, CSRF, вихід, публічні посилання й здачу в обох режимах.

4. **Доступність PostgreSQL.** Порт `192.168.1.13:5433` приймає TCP-з'єднання з LAN; прив'язка на всі інтерфейси. З'ясуй потреби легітимних клієнтів. Якщо зовнішній доступ не потрібен — обмеж його loopback або прибери публікацію; якщо потрібен — обмеж дозволеними адресами. Збережи Docker-з'єднання застосунку/воркера та чинні інтеграції. Не називай LAN-доступ доказом доступності з Інтернету чи обходу пароля.

5. **Квоти ШІ.** П'ять підключень мають `quota_limits={}`, явних quota_group немає: Gemini ×2, OpenRouter, Groq, Cloudflare. Встановлюй лише підтверджені бюджети конкретних акаунтів; незалежність двох Gemini-ключів не припускай автоматично. Якщо реальні значення неможливо отримати з доступних налаштувань/кабінетів, запитай потрібні значення, продовжуючи інші виправлення. Не підмінюй невідомі квоти вигаданими числами або «необмежено» й не позначай цей пункт завершеним без фактичного налаштування.

6. **Захист облікових записів.** `AUTH_PASSWORD_VALIDATORS=[]`, використовується стандартний ModelBackend; у teacher_login та встановленому middleware не знайдено throttling. Увімкни належну перевірку нових/змінених паролів, не змінюючи чинні паролі. Додай тимчасове обмеження частих невдалих входів, узгоджене між кількома Gunicorn-процесами. Врахуй спільний шкільний IP, не допускай постійного блокування вчителя та не записуй паролі в журнали. Перевір наявність зовнішніх захисних механізмів, перш ніж дублювати їх.

Порядок роботи: резервна копія й план відкату → ізольовані виправлення → цільові тести → перевірений випуск → контрольоване розгортання й фінальний звіт. Шлях штатного оновлення перевіряй на ізольованій копії або безпечним dry-run, не запускаючи зайве оновлення виробничої системи. Не запускай одночасні розгортання; використовуй блокування обслуговування.

Не змінюй чинні оцінки, учнівські спроби, завдання та медіа. Для перевірок використовуй синтетичні дані; нове передавання реальних робіт зовнішнім ШІ цим промтом не дозволяється. Не вважай успішний API-виклик доказом правильності оцінки. Не розширюй завдання до сторонніх сервісів сервера.

У фінальному звіті дай статус кожного з семи початкових зауважень окремо: Git-оновлення, Scout, HTTPS, PostgreSQL, приватні .env-копії, квоти, захист входу. Для кожного — фактична зміна, перевірка та залишкові обмеження. Невідомі або неперевірені речі не позначай як виправлені.
