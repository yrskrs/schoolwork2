# Як SchoolNet формує запит до ШІ та що потрібно перебудувати

Дата: 09.11.2026. Версія коду: 4.8.13n. Це аналіз локального коду та синтетичні перевірки. Запити до справжнього провайдера й аналіз конкретної проблемної роботи поки не виконувалися. Алгоритм оцінювання на цьому етапі не змінено.

## Головний висновок

Проблема виникає ще до відправлення запиту: система визначає роль джерел, скорочує текст і локально вирішує, що саме задав учитель. Потім ШІ отримує ці рішення разом із матеріалами. Після відповіді система додатково змінює її структуру та оцінку. Отже, перевіряти потрібно весь шлях від початкових джерел до збереженого результату.

Поточний шлях у скороченні:

**Натискання перевірки → черга → правила класу → читання роботи → читання матеріалів → визначення обсягу → побудова промпту → вибір моделі → скорочення для провайдера → знеособлення й адаптація медіа → API → перевірка та корекція відповіді → збереження → показ учителю.**

## 1. Два процеси, які зараз можуть розходитися

| Процес | Коли запускається | Що робить |
| --- | --- | --- |
| Аналіз умови | Окрема фонова задача `understanding`; також існують виклики через інтерфейс завдання | Читає умову та матеріали, визначає завдання, формує пояснення, зберігає `ai_task_understanding` з відбитком джерел. |
| Перевірка роботи | Одиночна, пакетна перевірка вчителем або самоперевірка учня | Повторно читає джерела, визначає обсяг роботи, складає запит, викликає модель, обробляє й зберігає результат. |

Другий процес не використовує результат першого як єдиний затверджений план. Він робить власний локальний аналіз; кешоване пояснення може бути додане до запиту лише як допоміжний контекст, якщо воно має `analysis_mode=ai` та відповідний відбиток.

## 2. Поточні етапи перевірки

| № | Етап | Що фактично відбувається | Результат етапу |
| --- | --- | --- | --- |
| 1 | Прийняття запиту | Перевіряються права. Беруться обрана схема оцінювання, ГР, додатковий промпт і режим мислення. Для самоперевірки перевіряються дозвіл і квота. | Запис `AIJob` у БД. |
| 2 | Фонова черга | Worker забирає завдання. Повторно перевіряється доступ. Для оцінювання об’єкти завдання й роботи читаються з актуальної БД. | Параметри перевірки та поточні дані, без повного незмінного знімка джерел. |
| 3 | Правила оцінювання | Береться політика конкретного класу; явний вибір учителя може її замінити для цього запиту. Визначаються критерії та активні ГР. | Шаблон, правила, ГР. |
| 4 | Читання роботи учня | Додаються коментар, посилання, вкладення, текстові витяги, візуальні матеріали й повідомлення про недоступні джерела. Читання підтримується не для всіх форматів однаково. | `text_parts`, `inline_media`, обмеження прочитаного. |
| 5 | Читання матеріалів учителя | Файли поділяються на головні й довідкові. Без явного вибору головний файл може визначатися за назвою та розширенням, якщо файлів більше одного. Довідковий текст уже тут скорочується. Посилання додаються окремо. | `primary`, `reference`, медіа, `coverage`. |
| 6 | Визначення заданого | Локальні правила шукають конкретні номери, кількість вправ, проєкт, запитання, вимоги й критерії. Пріоритет: опис/назва → критерії → головний файл → інші джерела умови → загальні правила якості. | `scope`: обов’язкові й незадані вправи, очікуваний результат, план оцінювання. |
| 7 | Побудова запиту | `build_assessment_request()` поєднує правила, умову, матеріали, роботу, критерії, історію повторної здачі, відомості про походження та JSON-схему відповіді. Матеріали знову фокусуються й скорочуються. | Текст запиту й системна інструкція. |
| 8 | Вибір моделі | Перебирається черга підключень/моделей. Перевіряються можливості, приблизний обсяг, зображення, зайнятість, квоти та таймаут. Для Gemini, Groq і OpenRouter будується компактний варіант тексту. | Окремий варіант запиту для спроби. |
| 9 | Підготовка відправлення | Знеособлюються текст та назви, застосовуються правила приватності. PDF залишаються документами або перетворюються на сторінки залежно від маршруту. Медіа оптимізуються; перевіряються ліміти. | Фактичне тіло API-запиту. |
| 10 | Виклик API | Адаптер формує формат провайдера. Помилка, квота або непридатна відповідь можуть спричинити повтор, перехід до наступної моделі чи відкладення. | Відповідь або помилка спроби. |
| 11 | Перевірка й корекція | Перевіряються JSON і бал; кількість завдань узгоджується з локальним `scope`. Змінюються повідомлення про незадані вправи, критерії, ГР, попередження та непідтверджені твердження. За правилами перевірюваності оцінка може блокуватися або обчислюватися з перевірених ГР. | Оброблений результат, який може відрізнятися від відповіді моделі. |
| 12 | Збереження й показ | Записуються рекомендована оцінка, звіт, ГР, модель, токени, статус. Формується окремий текст для учня. Рекомендація ШІ відділена від остаточного рішення вчителя. | Звіт у кабінеті та результат `AIJob`. |

Окремо може виконуватися підготовка матеріалів `prepare`: вона прогріває витяги й кеш без виклику API та без використання учнівської квоти.

## 3. Що саме входить до запиту

| Частина | Джерело |
| --- | --- |
| Системна інструкція | Особливий промпт перевірки або промпт шаблону; стандартний шаблон замінюється базовою роллю асистента; додаються загальні правила перевірки. |
| Умова | Назва, опис і приватні вказівки вчителя для ШІ. |
| Налаштування | Паралель класу, предмет, критерії, ГР, групова робота, дозвіл ШІ, допуск детектора. |
| Попередня інтерпретація | Локальний `scope`; за умовами актуальності — кешоване пояснення завдання. |
| Навчальні джерела | Головна умова, скорочені довідкові тексти, витяги посилань та обмеження читання. |
| Робота | Текст файлів, коментар, вміст доступних посилань, візуальні докази. |
| Додаткові дані | Ознаки походження, факти збігів, попередні зауваження при повторній здачі. |
| Формат відповіді | Схема JSON з оцінкою, критеріями, завданнями, ГР, доказами та рекомендаціями. |
| Медіа | Окремі вкладення PDF/зображень; вони не є просто частиною текстового промпту. |

Важлива деталь для подальшого виправлення: у `evaluate_submission_with_gemini()` спочатку збирається великий старий `prompt_lines` та старі інструкції. Перед циклом API вони замінюються результатом `build_assessment_request()`. Виправлення лише старих текстів може взагалі не змінити відправлений запит. Потрібно перевіряти кінцевий payload після всіх перетворень.

## 4. Виявлені проблеми та ризики

| Пріоритет | Спостереження | Підтвердження та наслідок |
| --- | --- | --- |
| Високий | Скорочення може прибрати змістову умову | Синтетичний приклад відтворено: після 1494 символів довідки система зберегла «Вправа 2. Обчислити результат», але відкинула окремий абзац зі ставкою 7% і округленням. Абзац не містив ключових слів. Це доведена втрата тексту; наявні медіа іноді можуть компенсувати її, але їх прочитання не можна припускати. |
| Високий | Головний файл передається до resolver по-різному | При оцінюванні заповнюється `primary_task_content`; при аналізі умови головний і довідковий текст об’єднано лише в `teacher_files_content`. Це підтверджено викликами в коді; вплив на конкретну роботу потребує прикладу. |
| Високий | Немає повного знімка на момент постановки в чергу | Зберігаються ID та параметри. Worker читає актуальні об’єкти. Якщо до виконання відредагувати умову чи критерії, перевірка може використати вже іншу версію. |
| Високий | Повторна інтерпретація та корекція результату | Модель отримує можливість уточнити завдання, але після відповіді лічильники знову прив’язуються до локального `scope`. Помилка першого локального рішення може пережити уточнення моделі. |
| Середній | Неповна актуалізація кешованого аналізу | Зміна `teacher_ai_instructions` або `allow_ai_usage` не змінює `assignment_fingerprint`; це відтворено. Самі нові вказівки потрапляють до поточного запиту, але старе кешоване пояснення може залишатися поруч із ними. Зовнішні URL входять до відбитка, їхній поточний вміст — ні. |
| Середній | Одне джерело проходить кілька скорочень | `teacher_materials()` → фокусування в `build_assessment_request()` → повторне скорочення → компактна версія для частини провайдерів. Немає єдиного списку всіх вилучених змістових фрагментів. |
| Середній | Головний файл може обиратися евристикою | Назва на кшталт «інструкція» та розширення дають бали. Якщо файл один і не позначений учителем, він не стає головним за цією евристикою. Варто показувати роль джерела явно. |
| Середній | Вміст текстового запиту залежить від провайдера | Компактний режим використовується для Gemini/Groq/OpenRouter; він може вилучати додаткові довідкові абзаци. Зміна моделі може змінити не лише оцінювання, а й доступний текст. |
| Середній | Наявні журнали не відтворюють весь контекст | Є параметри, події, токени, звіти та фрагменти промпту в помилках. Це не повний незмінний пакет відправлення з усіма версіями джерел і перетвореннями. |

Ці висновки не доводять причину помилки будь-якої конкретної здачі. Для цього потрібен контрольний приклад: точна умова, матеріали, робота, параметри й очікуваний результат.

## 5. Які етапи має проходити перебудована система

**Знімок джерел → ролі джерел → повне читання → узгоджена умова → план перевірки → добір доказів → перевірка повноти → перегляд пакета → адаптація до API → перевірка відповіді → прозоре рішення → збереження.**

| № | Етап | Що має бути на виході та коли йти далі |
| --- | --- | --- |
| 1 | Зафіксувати версію перевірки | Один `run_id`, версії умови, роботи, критеріїв, файлів і налаштувань. Редагування створює нову версію, а не змінює вже запущену перевірку. |
| 2 | Зафіксувати роль кожного джерела | Умова, довідка, зразок, критерії, робота учня. Евристичний вибір видимий учителю; суперечливе джерело не стає головним мовчки. |
| 3 | Прочитати джерела | Повні витяги з адресами: файл, сторінка, слайд, аркуш, комірка. Окремо статуси: повністю, частково, недоступно. Оригінал зберігається локально. |
| 4 | Узгодити обов’язкове завдання | Єдиний структурований опис того, що задано, що не задано, який результат очікується. Для кожної вимоги — посилання на джерело. Якщо обсяг неможливо визначити, потрібне уточнення вчителя. |
| 5 | Побудувати план перевірки | Список «вимога → критерій → потрібний доказ → ГР/правило бала». Теорія та приклади не створюють додаткових обов’язків. Пояснення учню та перевірка використовують ту саму версію плану. |
| 6 | Відібрати докази | Потрібна вправа разом із продовженнями, посиланнями на зразки й залежностями. Скорочується лише підтверджено зайве; реєструється, що вилучено й чому. |
| 7 | Перевірити повноту | Для кожної обов’язкової вимоги відомо, чи є достатні дані. Недоступний файл не означає невиконане завдання. Якщо основне неможливо перевірити, потрібен статус ручного уточнення. |
| 8 | Сформувати доступний для перегляду пакет | Учитель бачить: умову, план, джерела, фрагменти, обмеження й обсяг. Зберігається локальний маніфест та відбиток пакета. Перегляд доступний без платного API-виклику. |
| 9 | Адаптувати пакет для моделі | Змінюється транспортний формат. Набір вимог і зміст доказів зберігаються. Якщо модель не вміщує пакет або не підтримує потрібні медіа — обирається інша модель або повертається зрозуміла причина. |
| 10 | Отримати та перевірити відповідь | Сувора схема; відповідь на кожний пункт плану; перевірні посилання на докази; окремо «немає», «частково» та «неможливо перевірити». Нові вигадані вимоги відхиляються. |
| 11 | Застосувати правила рішення | Шкала й обчислення прозорі. Будь-яка серверна зміна зберігає значення до/після та причину. Припущення про походження роботи відділені від змістового бала. |
| 12 | Зберегти й показати результат | Пов’язані знімок, план, відправлений пакет, модель, відповідь і зміни сервера. Учитель отримує можливість перевірити причину кожного висновку та приймає остаточне рішення. |

## 6. Послідовність майбутніх змін

1. **Зафіксувати контрольні приклади.** Взяти ваші проблемні завдання; для кожного записати очікуваний обсяг, вимоги та неприйнятні висновки.
2. **Додати діагностику без зміни оцінювання.** Локальний перегляд остаточного тексту, інвентар медіа, знімки джерел та журнал скорочень. Це покаже, що реально побачила модель.
3. **Уніфікувати план завдання.** Спільний шлях головного файла, повна актуалізація кешу, одна версія вимог для пояснення та перевірки.
4. **Замінити добір контексту.** Прибрати видалення умов лише за ключовими словами; зберігати продовження, залежності та джерела доказів. Додати перевірку покриття перед відправленням.
5. **Спростити побудову промпту.** Один активний збирач; окремі правила, дані та схема; адаптери провайдерів не змінюють зміст завдання.
6. **Зробити обробку відповіді прозорою.** Валідація за планом, облік серверних виправлень, повторна оцінка лише при обґрунтованій причині.
7. **Перевірити на локальних прикладах і потім на API.** Спочатку детерміновані тести без мережі; потім однакові пакети для вибраних моделей. Порівнювати відповідність вимогам, докази, помилкові зауваження, вартість і час.

Ознака готовності: можна відкрити будь-яку перевірку й побачити, з якого фрагмента походить кожна вимога, які докази було передано та чому виставлено конкретний бал.

## 7. Локальне середовище для наступних ітерацій

Підготовлено окремий `compose.ai-lab.yaml`: проєкт `schoolwork2-ai-lab`, PostgreSQL, сайт, worker і Python runner. У всіх чотирьох сервісів `restart: "no"`. База, медіа та кеш мають власні томи. Порт сайту прив’язано до `127.0.0.1:8010`; PostgreSQL не публікує порт. Оновлювач сервера не запускається.

Код підключено з поточної папки для розробки. Після зміни Python-файлів виконайте `bash scripts/ai-lab.sh restart`. Після зміни залежностей або Dockerfile — `bash scripts/ai-lab.sh up`. Для нових міграцій також використовуйте `up`: запуск сайту виконує `migrate`.

| Дія | Команда з кореня проєкту |
| --- | --- |
| Зібрати, запустити й створити списки | `bash scripts/ai-lab.sh up` |
| Перевірити стан | `bash scripts/ai-lab.sh status` |
| Перевірити вхід і списки | `bash scripts/ai-lab.sh verify` |
| Подивитися локальні реквізити | `bash scripts/ai-lab.sh credentials` |
| Перезапустити сайт і worker після змін коду | `bash scripts/ai-lab.sh restart` |
| Переглянути журнали | `bash scripts/ai-lab.sh logs` |
