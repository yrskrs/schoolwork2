# Розбір звіту «Server Load And Performance Audit 2026-11-10»

**Джерело:** зовнішній файл `SERVER_LOAD_AND_PERFORMANCE_AUDIT_2026-11-10.md`, не код проєкту.  
**Перевірка:** 10.11.2026, лабораторний Docker (`127.0.0.1:8010`) і сервер (`192.168.1.13:8080`).

## Вердикт

Звіт **правильно вказує напрямок** проблеми: сторінка `/submission/<id>/` справді була повільною через синхронну перевірку дублікатів і зайві запити. Але **абсолютні цифри завищені**, а частина тверджень не перевірена. Код виправлень був у робочій копії, але **не закомічений і не задеплоєний** — саме тому сервер 4.8.16 досі відкривав роботу 435 за ~2.16 с.

## Що підтвердилося

| Твердження | Вердикт |
|---|---|
| `submission_detail` повільний через `check_submission_duplicates` | **Так.** Baseline: 62 SQL-запити, 601 мс холодний / 69 мс теплий на лабораторній роботі 1118. |
| Перевірка співавторства виконувалася до перевірки збігу файлів | **Так.** У коді `is_coauthor` тепер обчислюється лише всередині `if is_binary_match or is_text_match:`. |
| N+1 у `assignment_submissions` через відсутній `select_related('assignment')` | **Підтверджено**, `assignment` додано. |
| Зайві запити `submission.files` у `submission_detail` | **Підтверджено**, додано `prefetch_related('files')`. |
| Дублікат ключа `ai_authorship_state` у batch API | **Підтверджено**, дубль прибрано; поле лишилося один раз. |
| Важкі C2PA/метадані не виконуються при перегляді сторінок | **Так**, вони в `ai_worker`/AI job, не в `submission_detail`. |

## Що не підтвердилося або завищено

| Твердження | Вердикт |
|---|---|
| «11 мс і 10 запитів після фіксу» | **Не відтворено.** На lab: 27 мс і 26 запитів (теплий кеш), 601→27 мс і 62→26 запитів — покращення є, але не 10 запитів/11 мс. |
| «2.0 с → 11 мс, прискорення у 180 разів» | **Завищено.** На сервері 435 досі **2.16 с**, бо виправлення не задеплоєні. Локальні цифри залежать від кешу й даних. |
| «8 мс на `/api/submission-notifications/`» | **Не перевірено**; окремого навантажувального тесту не було. |
| «35 тестів за 8.76 с» | **Вузька вибірка.** Профільні 122 тести проходять, але це не повний регресійний набір. |
| «Повністю усунуто» | **Ні.** Потрібен деплой і повторний замір на сервері. |

## Ризики, які звіт не згадав

1. **24-годинний кеш дублікатів міг бути застарілим**: якщо пізніше з’являється копія або змінюється файл учителя, сторінка ще добу показувала б старий результат.
   - **Виправлено:** TTL зменшено до **1 години**, ключ включає `assignment_id`; кеш скидається при зміні хешу файлу.
2. **Фільтр за розширенням** при порівнянні файлів учителя може пропустити міжформатний збіг (наприклад, `.docx` vs `.pdf`).
   - Залишено як компроміс продуктивності; це треба перевірити на реальних кейсах.
3. Кеш зберігає `duplicate_student_name`; для учнівських посилань це далі приховується `scope_duplicate_info`, але кеш не можна віддавати без цієї обгортки.

## Висновок

- Аудит **корисний** як діагностика: він знайшов реальні N+1 та зайву роботу з диском.
- Його **абсолютні обіцянки** (11 мс, 10 запитів, 180×) не підтверджені.
- Виправлення закомічені з безпечнішим кешем (1 година) і мають бути задеплоєні; після деплою потрібен повторний замір саме на сервері.
- Для остаточної впевненості варто додати регресійний тест кількості запитів для `submission_detail`.
