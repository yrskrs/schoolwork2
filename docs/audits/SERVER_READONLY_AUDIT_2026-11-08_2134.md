## Виявлені проблеми та ризики

### 1. Високий операційний пріоритет: штатне встановлення оновлень блокується Git-станом

Серверний `git status --short` у фінальному знімку містить **86 записів** змінених/невідстежуваних файлів. Виконуваний код збігається із серверними файлами, але вони не узгоджені з Git-історією цієї копії.

Обидва штатні шляхи мають явну заборону продовжувати за такого стану:

- `scripts/update.sh:14` — відмова, якщо `git status --porcelain` непорожній;
- `scripts/updater_service.py:304–305` — аналогічна відмова для оновлення/перезбірки.

**Вплив:** перевірка наявності нової версії може працювати, а фактичне встановлення штатним оновлювачем відмовиться. Успішні спеціальні сценарії ручного розгортання не доводять працездатність цього штатного шляху.

**Що варто зробити окремим погодженим завданням:** узгодити установлені зміни з Git, спершу виключивши приватні файли. Не виконувати сліпий `git reset` чи `git add -A`: перше може стерти установлені виправлення, друге — додати приватні копії конфігурації. Сам оновлювач для перевірки не запускався.

### 2. Середній пріоритет: Llama 4 Scout помилково визнана текстовою

У чинній черзі ввімкнено `@cf/meta/llama-4-scout-17b-16e-instruct`. Діагностичний виклик каталогу повернув:

```json
{"enabled_in_queue": true, "supports_vision": false, "max_images": 0}
```

При цьому [офіційна картка Cloudflare](https://developers.cloudflare.com/workers-ai/models/llama-4-scout-17b-16e-instruct/) прямо вказує підтримку Vision і мультимодальність.

**Причина:** окремого запису Scout у каталозі немає, а евристика Cloudflare в `feed/ai_model_catalog.py` шукає слова `vision`, `vl`, `multimodal`, `11b-vision`, яких у цій назві немає.

**Вплив:** придатна резервна модель може помилково виключатися з візуальних перевірок. Це обмежує вибір провайдерів та очікувану паралельність. Неправильність метаданих підтверджена без надсилання учнівських матеріалів; реальний API-виклик у цьому аудиті не проводився.

Qwen Cloudflare розпізнається як vision із лімітом 32, GLM — як текстова з лімітом 0: попередні зауваження щодо цих двох моделей не слід автоматично переносити на поточну версію. Для перевірки каталогу доступ до кешу обмежень був замінений лише в окремому діагностичному процесі, без зміни серверного коду/кешу.

### 3. Середній пріоритет: HTTPS-посилення cookie/HSTS залишається відкладеним

`manage.py check --deploy` повертає чотири попередження:

- `security.W004`: `SECURE_HSTS_SECONDS=0`;
- `security.W008`: `SECURE_SSL_REDIRECT=False`;
- `security.W012`: `SESSION_COOKIE_SECURE=False`;
- `security.W016`: `CSRF_COOKIE_SECURE=False`.

Безпосередньо через HTTPS сторінка входу видає CSRF-cookie без атрибута Secure. Параметр session-cookie також не Secure; авторизований вхід для перевірки її фактичного заголовка не виконувався. HTTPS сам працює, це не діагноз зламаного TLS.

Це **вже відоме відкладене рішення**, описане в `docs/plans/SECURITY_HARDENING_HTTPS_2026-11-08.md`. Публічний Funnel увімкнений, тому питання актуальне. Глобальне вмикання HTTPS-only параметрів без поділу LAN/Funnel може зламати вхід через LAN HTTP; виправляти навмання не можна.

### 4. Середній пріоритет: PostgreSQL доступний через мережевий порт 5433

Контейнер публікує 5433 на всіх host-інтерфейсах; TCP-з'єднання з аудиторського клієнта до `192.168.1.13:5433` прийняте. Вхід до БД через цей порт не виконувався, паролі не перевірялися.

**Вплив:** доступ до БД не обмежений лише внутрішньою Docker-мережею. Варто визначити, чи потрібен мережевий доступ до PostgreSQL, і окремо перевірити обмеження IP/firewall. Доступність із публічного Інтернету цим аудитом не встановлена; відкритий LAN-порт не є доказом зламу або обходу автентифікації.

### 5. Середній пріоритет: приватні .env-копії не виключені з Git

У корені серверної копії є шість `.env.bak-*`, включно з копіями випусків b/c/d/e/f. Вони відображаються як untracked; чинний `.gitignore` їх не охоплює.

**Вплив:** майбутнє масове додавання файлів у Git може випадково додати резервні конфігурації. Вміст файлів у цьому аудиті не читався й секрети не експортувалися.

Обмежувальні чинники: права файлів **0600**; `.dockerignore` виключає `.env*`; у перевіреному образі знайдено лише `.env.example`. Тобто **витік секретів не встановлено**. Питання слід вирішувати перед узгодженням Git зі встановленим кодом.

### 6. Середній пріоритет: локальні квоти ШІ не налаштовані

Усі п'ять підключень мають `quota_limits={}`; явних груп квот немає. Провайдери: Gemini ×2, OpenRouter, Groq, Cloudflare. Це не означає відсутність реальних обмежень у провайдерів — лише відсутність заповнених локальних RPM/RPD/TPM тощо.

**Вплив:** координатор не може заздалегідь спланувати невказані хвилинні/добові бюджети і більше покладається на фактичні відмови провайдера. Порожні групи консервативно об'єднують підключення одного провайдера. Без знання акаунтів не можна визначити, чи обидва Gemini-підключення справді мають спільну квоту.

Потрібно окремо звірити налаштування з кабінетами провайдерів. Конкретні значення лімітів у цьому аудиті не вгадувалися і не встановлювалися.

### 7. Середній пріоритет для публічного доступу: захист облікових записів потребує окремої перевірки

`AUTH_PASSWORD_VALIDATORS=[]`. У `teacher_login` і встановленому middleware не знайдено обмеження частоти невдалих входів. Публічна HTTPS-сторінка входу доступна; конфігурація публічного доступу — enabled, allow_without_link.

**Вплив:** стандартна перевірка якості паролів Django не налаштована; на рівні цього обробника входу не видно захисту від частих спроб. Це не доказ слабких поточних паролів. Зовнішні механізми захисту, якщо вони є, не підтверджувалися. Перебору паролів, тестових входів, створення/зміни облікових записів не було.

Окремо `ALLOWED_HOSTS=['*']` відповідає гнучкому LAN-сценарію, але для публічного використання варто переглянути допустимі домени. Це рекомендація посилення, а не встановлений обхід доступу.
