## Журнал виконання

1. Перевірено робочу копію: початковий HEAD `da89b3e`, незбережених змін не було. Інструкцій AGENTS.md у робочому дереві не знайдено.
2. Переглянуто README, Compose, залежності, моделі вчителя/завдань/сповіщень, хмарні клієнти, фонову чергу, навігацію налаштувань, backup/restore helpers та ізоляцію тестових БД.
3. Сервер 192.168.1.13 не змінювався; підключення до сервера та хмарних акаунтів не виконувалися. Секрети середовища не читалися.
4. Підготовлено цей план. Код можливості, міграції та зміни інтерфейсу ще не виконувалися.

## Наявні компоненти

- Django; серверний Compose використовує PostgreSQL 16, app, ai_worker та спільний media/cache.
- `scripts/backup.sh` зупиняє app/ai_worker, перевіряє дамп і media.tar.gz; `scripts/restore.sh` та `scripts/backup_tools.py` забезпечують повне серверне відновлення. Їх потрібно зберегти.
- `TeacherCloudStorage`, `feed/cloud_storage.py`, `feed/views_cloud.py` і готова картка підключень дають основу для Nextcloud та Google Drive. Переглянуті клієнти реалізують читання/імпорт; запис резервних копій потрібно додати.
- GoogleDriveClient.SCOPES містить drive.readonly: чинної авторизації недостатньо для upload. Потрібен дозвіл запису та повторне OAuth-підключення. API key для публічного імпорту не замінює таку авторизацію.
- `CloudImport` і worker показують наявний підхід до стійких завдань, прогресу та повторів. Черга резервування має мати власні стани й блокування.
- `SystemNotification` і центр сповіщень можна використати для повідомлень успіху/помилки після закриття вкладки.
- Наявні ZIP export/import завдань варто перевикористати після перевірки повноти: самі по собі вони не доводять збереження всіх здач, коментарів, оцінок, співавторів і зв'язків.
- Новий розділ резервування слід додати до наявних налаштувань. Для тестів уже є `schoolnet.test_settings` з тимчасовими медіа та SQLite в пам'яті.

## Запропонований порядок реалізації

1. Уточнити межі копії, значення «інший пристрій», формат архіву, історію версій, канали сповіщень та порядок розгортання.
2. Описати версійований формат перенесення даних учителя, сталі ідентифікатори, карту залежностей і правила повторного відновлення без дублів. Розділити особисту копію та повну адміністративну копію сервера.
3. Додати сховище зі стисненими незмінними блоками й контрольними сумами: повторно використовувати наявні блоки, передавати зміни, публікувати завершений маніфест лише після перевірки. Стару працездатну точку не замінювати незавершеною.
4. Додати необов'язкове шифрування паролем. Для автоматичних запусків спроєктувати захищене зберігання ключа; ключ відновлення не повинен залежати лише від утраченого сервера. Остаточний контейнер і формат залежать від уточнення щодо ZIP/7z.
5. Реалізувати Google Drive OAuth із правом запису та Nextcloud WebDAV; окремі простори двох сайтів і вчителів, повтори, таймаути, контроль цілісності й відновлення після переривання.
6. Додати стійку чергу ручних і планових запусків, блокування паралельних операцій, облік станів та сповіщення успіху/помилки.
7. Додати «Налаштування → Резервні копії»: підключення, вибір складу, пароль, розклад за Києвом, прогрес, статистика, журнал і перевірка копії.
8. Реалізувати пошук наявної копії з нового встановлення, попередній перегляд складу, безпечне відновлення з перевіркою власника та конфліктів.
9. Перевірити цикл backup/restore на синтетичних даних у відокремленому середовищі; після цього оновити довідку сайту, README, docs, CHANGELOG і версію. Фіксувати завершені етапи окремими комітами.
10. Після перевірок підготувати розгортання з локальною захисною копією, пробним відновленням, перевіркою стану сервісів і планом відкату; робочі дані не використовувати як тестовий майданчик.

## Обов'язкові перевірки

- Дані без файлів; матеріали вчителя; роботи/відповіді учнів; усі вибрані категорії разом.
- Незмінний повторний запуск не завантажує ті самі блоки; зміна одного об'єкта передає лише потрібні блоки; видалення не руйнує збережену точку відновлення.
- Копії без пароля та з паролем, неправильний пароль, зміна пароля, пошкодження, втрачений блок, архівні шляхи за межами каталогу, ліміти розпакування.
- Недоступна хмара, прострочений OAuth, відмова запису, брак місця, перерваний upload, перезапуск worker, два одночасні запуски, пропущений розклад.
- Ізоляція вчителів; повторний restore без дублів; відновлення на чистому сервері та поведінка при конфліктах.
- Статистика фактичних байтів/об'єктів, підтвердження цілісності та сповіщення після ручних і автоматичних запусків.

## Стан перевірок і відкриті рішення

Автоматичні тести ще не запускалися: функціональних змін немає. У поточному середовищі виявлено Python 3.14.8; команд docker і pytest у PATH немає. Потрібно підготувати ізольоване сумісне тестове середовище перед реалізацією.

Потрібно уточнити: особиста чи також повна серверна копія; новий браузер чи нове встановлення; звичайний ZIP/7z чи інкрементальний репозиторій з експортом архіву; збереження історії; сповіщення лише на сайті чи зовнішні; доступ до тестових хмар і спосіб майбутнього розгортання.

## Узгодження та реалізація

Замовник підтвердив: відновлення на новому встановленні після втрати сервера; особисті та повні адміністративні копії; вибір формату з поясненням; історія 30 днів; сповіщення на сайті; початкове налаштування обох хмар.

Додано спільне ядро ZIP / AES-256 ZIP та інкрементального сховища, потокову передачу архівів, перевірку контрольних сум, стійку чергу й розклад. Адаптер Django включає пов'язані завдання, здачі, оцінки, коментарі, списки й вибрані файли; особисті копії не переносять паролі облікових записів та права адміністратора. Фонове виконання приєднано до чинного ai_worker, тому штатні backup/update/restore продовжують зупиняти всіх процесів запису без нового сервісу.

Проміжна перевірка: 7 тестів графа SchoolWork з тимчасовою БД/медіа — OK; Django check — OK. Використано окреме /tmp середовище Python 3.14 / Django 5.2; це не тотожне production Python 3.12 / Django 6.1. Перевірки production-сумісності, PostgreSQL, інтерфейсу та реальних провайдерів ще попереду. Сервер і реальні хмарні акаунти не змінювалися.
